A systematic review of Held in Common at `main` (commit `fc49038`, 10 Nov 2026):
the `hic-commons` server (`commons/main.rs`), the desktop app (`src-tauri/`),
CI, Docker and the docs. It covers security, stability, how the code will grow,
and what the base needs so the planned work fits on top of it: sharing
datasets, commons governance, and federated adapters as described in the BRAID
fellowship case for support (WP3–WP4).

against the code; file and line references are to `fc49038`. Anything not
checked is marked **unverified**.

findings by severity, each with a fix. Section 3 is about the codebase itself.
Section 4 sketches the base the future features need. Section 5 is the order of

## 1. Summary

The core idea is sound and the code is small enough to fix properly now. One
binary runs as a node or a commons, identities are keypairs, versions are
content-addressed and signed, and a commons pins a handle to the first key
that shares it. What's already good:

- Handles are validated before they become file paths (`commons/main.rs:219-227`), so path traversal is closed.
- A strict Content-Security-Policy and security headers on every response (`main.rs:55-57`, `1773-1781`).
- Per-session CSRF tokens on publish and share, and `SameSite=Lax` cookies.
- A request body limit, and the role fixed to its data folder (`resolve_role`).
- An end-to-end federation test (35 checks) that runs on every PR.
- Signed, notarized macOS builds with secrets kept in a protected environment.

What needs work, in one line each:

1. **The desktop node is reachable from the whole local network** and its passphrases are cheap to crack.
2. **The desktop app trusts anything on port 8080.**
3. **A commons can be rolled back** to an older signed version, and **nothing can be withdrawn**, although the interface says it can.
4. **Writes aren't crash-safe**, and a damaged file can let someone re-register an existing handle.
5. **The signed format isn't specified**, so other tools (such as Python training scripts) can't reproduce or verify it, and a dependency change could silently break every signature.
6. **One 1,800-line file and no unit tests** make it hard for a newcomer to change anything safely.
7. **Data is stored as loose JSON files with no schema version**, which won't hold up for datasets, adapters and model versions.

## 2. Findings

Severity: **High** means fix before the next workshop or public use. **Medium**
means fix as part of hardening the base. **Low** means tidy up when nearby.

### High

**H1. The node accepts connections from the whole network.**
`main.rs:1812` binds `0.0.0.0`. The desktop app runs a node on every
interface, so anyone on the same Wi-Fi (a café, a conference, a workshop room)
can open its sign-in page and try passphrases. Confirmed on a running install:
`lsof` shows `*:8080 (LISTEN)`.
*Fix:* a node binds `127.0.0.1`. Only a commons binds to the network. Add
`HIC_BIND` for people who deliberately want a reachable node.

**H2. The desktop app trusts whatever answers on port 8080.**
`src-tauri/src/lib.rs`: `node_up()` only checks that a TCP port is open,
`open_when_up()` then loads it in the window, and `restart_node()` reports
success if anything is listening. Port 8080 is a common default for
development servers and containers. If one is running, the sidecar fails to
start and the window shows the other service, where the person may type their
passphrase.
*Fix:* choose a free port at launch, or at least check that `/health` answers
`"service":"hic-commons"` with a per-launch token passed to the sidecar.

**H3. Passphrases use a single SHA-256 and sign-in has no rate limit.**
`main.rs:397-403`. SHA-256 is designed to be fast, so a copied `handles/`
folder can be cracked offline, and together with H1 the sign-in form can be
guessed online.
*Fix:* Argon2id (the `argon2` crate) stored as a PHC string, upgrading old
hashes on the next successful sign-in. Limit sign-in attempts per handle and
per address.

**H4. Private keys are stored in plain text and can't be backed up or rotated.**
`main.rs:98-111`: `ed_priv` and `box_priv` sit unencrypted in
`handles/<handle>.json`. Because each commons pins a handle to its first key,
losing the laptop means losing that handle on every commons, permanently. A
fellowship that runs for a year needs composers to keep their identity
through a new laptop.
*Fix:* (1) an encrypted identity export and import; (2) key rotation, where
the old key signs a statement naming the new key and commons accept it;
(3) later, keys wrapped with a key derived from the passphrase, or held in the
macOS Keychain.

**H5. A commons can be rolled back to an older version.**
`inbox` (`main.rs:1431-1454`) stores any validly signed share, and
`save_remote` (`main.rs:262-266`) overwrites the previous one. Anyone holding
an older signed share (a commons operator, or someone who captured one) can
re-submit it and restore an old bio, a wider licence or an older visibility.
The test suite itself replays a captured activity and expects `202`.
*Fix:* refuse a share whose `created_at` is not newer than the stored one, and
keep the history (see section 4: each version names the previous one).

**H6. Withdrawal is promised but not built.**
The publish form says "If you later narrow visibility or withdraw, the commons
stops serving that version" (`main.rs:1227`; also `/about`, `main.rs:1503`).
There is no withdraw or delete action anywhere, so a shared profile stays on
every commons for good. Withdrawal is also central to the fellowship (the
Model Withdrawal Protocol) and to UK GDPR erasure requests.
*Fix:* a signed `Withdraw` activity. The commons removes the copy and keeps a
small record of the withdrawal (a tombstone), so a replay can't bring it back
(see H5). Until then, change the wording.

**H7. "Kept out of search" isn't implemented.**
The `commons` reach is described as "kept out of search" (`main.rs:1195`,
`1505`; `docs/ARCHITECTURE.md` §1), but nothing sends `noindex` (a search for
`noindex`/`robots` finds nothing).
*Fix:* add `<meta name="robots" content="noindex">` and an `X-Robots-Tag`
header to pages for `commons`-reach profiles, both on nodes and on the copies a
commons holds. Add a `robots.txt`.

**H8. Writes aren't crash-safe, and a damaged handle file can be taken over.**
`save_handle`, `save_version` and `save_remote` call `std::fs::write` directly
(`main.rs:228-241`, `262-266`), and only Ctrl-C triggers a clean shutdown
(`main.rs:1816`), not the SIGTERM that `docker stop` and the app's quit send.
An interrupted write leaves a cut-off file. `load_handle` treats an unreadable
file as "no such handle", so `/join` then lets someone register that handle
again and overwrite the original identity.
*Fix:* write to a temporary file, `fsync` it, then rename it over the old one.
Handle SIGTERM. Treat a file that won't parse as an error, not as missing.

**H9. A damaged key file is silently replaced with an all-zero key.**
`hex_to_32` (`main.rs:1309-1316`) fills any bad or short key with zeros, so
`publish` would sign with a known, worthless key without saying so.
*Fix:* return an error and refuse to publish.

### Medium

**M1. The signed format depends on library behaviour.**
`content_id` hashes whatever `serde_json` writes for the `Canonical` struct
(`main.rs:504-508`). That is stable today only because `serde_json::Value`
sorts object keys by default. If any dependency turns on serde_json's
`preserve_order` feature (Cargo combines features across the whole build),
every new hash changes and older copies stop verifying. Other languages can't
reproduce the bytes either, which matters as soon as a Python training script
needs to sign or check an adapter.
*Fix:* write the format down: RFC 8785 (JSON Canonicalization Scheme), a
fixed prefix inside what is signed (for example `hic/v1/profile`) so a
signature for one kind of object can't be reused for another, and published
test vectors. See section 4.

**M2. Only part of a share is signed.**
The signature covers the `cid` (`main.rs:1295-1296`), but the display name,
origin, origin label, encryption public key (`boxPublicKey`) and avatar
(deliberately left out, `main.rs:491-502`) aren't covered. Any of them can be
changed in transit or by a commons. A swapped encryption key matters as soon
as anyone encrypts to a member's federated key.
*Fix:* sign the whole object (section 4). If avatars stay outside the hash,
sign them separately.

**M3. "ActivityPub-ready" overstates what exists.**
`publicKeyPem` holds a hex Ed25519 key, not PEM (`main.rs:1642`). The actor's
`inbox` URL (`/ap/@handle/inbox`) returns 404, object ids don't resolve, and
there are no HTTP Signatures, so Mastodon and similar servers won't federate.
*Fix:* call it "ActivityStreams-shaped" in `/about` and the docs for now. If
real ActivityPub interoperation is wanted, add it later with HTTP Message
Signatures (RFC 9421) and FEP-521a keys.

**M4. Sessions never expire on the server.**
Sessions live in memory with no expiry (`main.rs:169`, `537-542`). The cookie
says 24 hours, but the token is valid until the process restarts.
*Fix:* store an expiry time with each session, check it on every request, and
clear old sessions periodically.

**M5. Members-only encryption protects less than the interface suggests.**
The server holds every member's private key next to the ciphertext
(`main.rs:455-489`), so anyone who can read the data folder can read
members-only profiles. Someone who joins after a version is published can't
read that version.
*Fix:* describe the real threat model in the docs and on `/about` ("protects
copies outside this node; doesn't protect against whoever runs the node").
Encrypting to keys held on members' own devices is a later step.

**M6. Share can be pointed at internal addresses.**
`/share` posts to any address a signed-in member types
(`main.rs:1379-1400`). On a hosted node with several members, that lets a
member make the server send requests to internal services (server-side request
forgery).
*Fix:* refuse private and link-local addresses unless the node is local, and
cap redirects.

**M7. Anyone can fill a commons.**
`/inbox` has no rate limit and accepts any number of new handles.
*Fix:* rate-limit `/inbox`. Add an optional steward approval queue for first
shares; this belongs with the governance work and the charter.

**M8. Every page reads every file.**
`all_handles` and `all_remotes` (`main.rs:243-288`) read the whole directory
on each request, and `handle_taken` runs on every share. That's fine for
hundreds of profiles and slow for tens of thousands.
*Fix:* put storage behind one module, with an index in SQLite and
content-addressed files for large data (section 4).

**M9. The macOS account name is sent to every commons.**
The desktop app labels the instance "`$USER`'s node" (`lib.rs`,
`instance_label`), and that label travels with every share as `originLabel`.
*Fix:* ask for a node name in the chooser, defaulting to something neutral.

**M10. Every page loads Google Fonts.**
`main.rs:746-748`. Each visitor's IP address goes to Google, which doesn't fit
the project's privacy stance, and the fonts don't load in a workshop room
without internet access.
*Fix:* serve the fonts from the binary, as `style.css` already is.

**M11. The desktop app grants the web page more than it uses.**
`src-tauri/capabilities/default.json` lets the window's JavaScript run the
sidecar with any arguments (`shell:allow-execute`, `args: true`), but only the
Rust side starts the sidecar. `tauri.conf.json` sets `"csp": null`.
*Fix:* remove that permission and set a CSP for the local screens.

**M12. A crashed server stays down, and its logs disappear.**
The sidecar's output goes to stderr only (`lib.rs`, `spawn_server`), and
nothing restarts it.
*Fix:* `tauri-plugin-log` writing to a file in the app's data folder; restart
the sidecar with a back-off; a "Copy diagnostics" button for support.

**M13. No automatic updates.**
The formats will change over the next year. Without updates, workshop
participants will be on different versions that can't talk to each other.
*Fix:* `tauri-plugin-updater` against the signed release, and a protocol
version in every share so a commons can explain a mismatch.

**M14. The Docker image isn't reproducible.**
`commons/Dockerfile` doesn't copy `Cargo.lock`, so each build resolves
dependencies again. It runs as root and has no `HEALTHCHECK`.
*Fix:* copy the lock file and build with `--locked`, run as a non-root user,
add a health check.

### Low

- **L1.** The CSP comment says "no scripts at all" but the policy allows `script-src 'self'` for `avatar.js` (`main.rs:53-57`).
- **L2.** `error_page` returns HTTP 400 for server-side failures too (`main.rs:1720-1726`).
- **L3.** `publish` reads the handle record before taking the write lock (`main.rs:1241` vs `1283`) and ignores a failed save (`main.rs:1304`). A share in between can lose its `shared_to` entry, and a failed save goes unnoticed.
- **L4.** The room-commons address detection (`lib.rs`, `lan_url`) needs a route to the internet, so it finds no address on a closed workshop network.
- **L5.** The version number is in three places (`commons/Cargo.toml`, `src-tauri/Cargo.toml`, `tauri.conf.json`).
- **L6.** *Unverified:* closing the window may leave the app running with no way to reopen it on macOS. Seen once during testing; not reproduced.

## 3. The codebase

**Split `commons/main.rs` into modules.** It holds the data model, storage,
cryptography, federation, HTML pages, JSON API and configuration in one file.
A suggested layout, one concern per file:

```
crates/
  hic-core/      types, canonical form, signing, verification, schema versions
                 (no web code: reusable by future adapter tools, a Python
                 binding or WebAssembly)
  hic-server/    config.rs, store/, federation.rs, auth.rs, web/ (pages), api.rs, ap.rs
apps/desktop/    the Tauri app (today's src-tauri/)
```

A Cargo workspace keeps one lock file and one version.

**Move global state into `AppState`.** `BANNER` and `PUBLIC_URL`
(`main.rs:47-51`) are process-wide statics, which makes the server hard to
test in-process.

**Add unit and integration tests.** There are no Rust tests today
(`#[test]` appears nowhere). All coverage is the bash script. Add:
- test vectors for the canonical form and signatures (they double as the specification);
- unit tests for `verify_inbound`, `resolve_role` and handle rules;
- in-process HTTP tests with `tower::ServiceExt::oneshot`, which run in milliseconds;
- keep `scripts/test-federation.sh` for full end-to-end runs.

**Use typed errors and structured logs.** Errors are strings today, and
logging is `println!`. Use `thiserror` for an error type that maps to HTTP
status codes, and `tracing` for logs a steward can search.

**Add a version to every stored record and every share.** No file says which
format it's in, so the first format change becomes guesswork. Add
`"schema": 1` now, while every file is ours.

**Remove the legacy prototype from `main`.** The repository root still holds
the earlier Leptos onboarding app (`Cargo.toml`, `src/`, `styles/`, a compiled
`dist/` with WebAssembly checked in) and `node/`. Running `cargo build` at the
root builds the wrong program. Tag the current commit as `legacy-onboarding`,
then delete those paths.

**Add checks to CI:** `cargo fmt --check`, `cargo clippy -D warnings`,
`cargo deny` (licences and known vulnerabilities), a pinned toolchain
(`rust-toolchain.toml`), and builds with `--locked`.

## 4. A base for datasets, governance and federated adapters

The BRAID case for support describes where this goes: each composer's machine
is a node that holds their catalogue and rights record, and lists them in a
federated dataset built on FDCCC, so the collective can see what is
contributed and on what terms while the audio stays local (WP3). Composers
train adapters on their nodes. Each contribution the collective licence admits
produces a numbered model version sent to every node. Withdrawal removes one
composer's adapter and issues a new version without it (WP4).

None of that needs building yet. But the base should be shaped so it slots
in. Six changes do most of the work:

**1. One signed envelope for everything.** Today only profiles are signed. Use
one format for every object:

```
{
  "schema": "hic/v1",
  "type": "Profile" | "DatasetListing" | "RightsRecord" | "Licence"
        | "Adapter" | "ModelVersion" | "Withdraw" | "Decision" | "KeyRotation",
  "author": "<ed25519 public key>",
  "created_at": 1794249051,
  "prev": "<cid of this author's previous object of this kind, or null>",
  "body": { ... type-specific ... }
}
cid = sha256(JCS(envelope)); signature = ed25519("hic/v1/" + type + cid)
```

`prev` links each author's versions into a chain. That fixes rollback (H5),
gives a full history, and lets anyone check that nothing was removed, much as
the Guild Register is hash-chained.

**2. Listings, not files.** A `DatasetListing` names items by hash, size,
media type, rights record and licence. The audio itself stays on the node.
This is the "federated dataset" of WP3, and the commons stores only listings.

**3. Large files never go through `/inbox`.** Adapters are tens to hundreds of
megabytes; datasets are larger. Keep `/inbox` for small signed objects. Large
files go in a content-addressed store (`blobs/<sha256>`), fetched by hash with
resumable downloads, and the signed object names the hash.

**4. Nodes pull; they don't wait to be pushed to.** Composers' laptops sit
behind home routers and are often asleep, so a commons can't reliably push "a
numbered version sent to every node". Instead, each commons publishes an
append-only feed of signed objects, and nodes fetch everything after the last
item they saw. The same feed works as an audit log for governance.

**5. Governance as signed objects.** A commons charter, its stewards' keys and
each decision (admitting a member, admitting an adapter under the licence)
become signed `Decision` objects in the feed. A small policy check can then
answer "does the licence admit this adapter?" in code, and the feed records
why each model version contains what it does.

**6. Withdrawal as a first-class object.** A `Withdraw` names what is being
withdrawn (a profile, a dataset item, an adapter). The commons drops it and
keeps the tombstone. The next `ModelVersion` leaves the adapter out. This is
the same operation for a profile today (H6) and for an adapter in WP4.

Two supporting pieces:

- **Identity that lasts:** key backup, rotation and multiple devices (H4), so a composer keeps their identity for the whole project.
- **Python interoperability:** the training script composers run will almost certainly be Python. With a written specification and test vectors (M1), a small Python package can check and create the same signed objects, or the script can register an adapter through the node's local API.
